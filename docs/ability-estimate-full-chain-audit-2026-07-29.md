# 能力画像 / 能力估测全链路审计报告

审计日期：2026-07-29  
审计范围：当前仓库代码、Git 历史、Supabase `training_records` 生产数据（只读）  
生产数据窗口：2026-05-20 至 2026-07-19，共 102 条训练记录  
审计原则：未修改生产算法，未写入或删除数据库数据；仅新增审计测试与本报告

## 一、执行摘要

已确认存在确定性错误，且用户描述的三类异常都能由真实代码和真实记录复现。

最严重的两个问题是：

1. **旧版维度子分被当成百分制原始分。** 2026-05-23 的 16 条记录使用 `score/maxScore` 结构，例如 `22/30、18/25、14/20、12/15、6/10`。这些值原本分别相当于 `73.3、72、70、80、60` 分，但 `projectAbilityDimensions()` 忽略 `maxScore`，直接使用 `22、18、14、12、6`。真实的 72 分自由辩论记录因此在第二个历史快照生成了 **22.1/100** 的综合锋力。该值不是合理的原始能力分，也不是有意设计的总分贡献值，而是**旧分制子分被错误当成百分制后的中间聚合结果**。
2. **后端的“不适用/null”被前端转成 0。** 后端会把本次训练不覆盖的能力写入历史点为 `null`，但前端执行 `Number(rawValue)`；JavaScript 中 `Number(null) === 0`。所以防守稳定会在非防守/非自由辩训练处画出 0，反压能力会在立论/结辩等不覆盖它的训练处画出 0，形成用户看到的锯齿。这些 0 不是真实得分，也没有进入后端顶部估测，但污染了图表和来源卡片。

其他重要结论：

- 新版训练写入的是五个 **0～100 原始维度分**；`weightedContribution` 没有单独存储。
- 训练总分由后端按当前模式权重重算，但被强制限制在 **30～100**。因此“五维全为 0”会得到总分 30，口径自相矛盾。
- 顶部 `/100` 数值不是最新一次、简单平均、线性回归或趋势预测；它是“30 天断点分包 + 包内指数加权 + 包间动态融合”的历史平滑值。
- 曲线点也不是单次原始分，而是“截至该次训练的平滑估测快照”。数据来源卡片的“总分”是该次训练总分，“维度分数”却是平滑快照，当前页面没有展示该次训练投射出的原始能力分。
- 不同难度直接混合。能力层额外使用固定加分：新手 `-4`、校赛 `+2`、市赛 `+7`；没有百分位、等值量表、配对样本校准或经验验证。
- 数据库没有 `scoringVersion`、`rubricId`、`applicable`、`rawScore`、`weightedContribution` 字段。102 条记录中：91 条有维度数组、11 条维度数组为空；16 条为旧版子分制、75 条为新版百分制；10 条自由辩记录使用旧字段“团队协同与战术意识”。
- 16 条旧分制记录影响 7 个用户/空间画像。用只读副本按 `score/maxScore*100` 并做旧字段别名适配复算，7 个画像的综合值变化范围为 `0～+46.5`，其中用户描述样本所在画像从 `68.0` 变为 `81.7`。这是修复影响估算，不是已执行迁移。

综合统计合理性评分：**41/100**。平滑公式本身可计算、可复现，但输入口径、历史版本、难度校准和前端缺失值语义不足以支撑“稳定、统一的能力估测”这一产品承诺。

### P0 修复进展（2026-07-29）

本报告完成后，已按确认优先级实现两个 P0 修复：

1. **前端 null 修复已完成**：能力历史值改由 `normalizeAbilityHistoryValue()` 解析；`null/undefined/空字符串/非法值` 保持缺失，真实数值 0 仍为有效点。图表不再把不适用维度画成 0。
2. **旧数据读时归一化已完成**：`projectAbilityDimensions()` 在进入能力投射前，对 `maxScore != 100` 的历史子分执行 `score/maxScore*100`，并适配旧自由辩字段“团队协同与战术意识”。没有覆盖或删除数据库原记录。

真实 72 分旧记录形态的回归夹具现复算为综合锋力 79.8，不再产生约 22.1 的错误量级。最新版评分规则、样本锚定库和难度修正公式仍在开发，本次没有调整这些公式。

### 2.3 缺失值与 0 的实际处理

确认没有在后端能力主链中使用 `score || 0`、`Number(score) || 0` 或 `parseFloat(score) || 0` 把合法 0 与缺失混合。后端关键行为如下：

- `parseFiniteScore()`：`0` 有效；`null/undefined/''/boolean/NaN` 返回 `null`。
- `projectAbilityDimensions()`：字段缺失、名称不匹配、非法值不会生成该能力更新。
- `buildAbilityEstimate()`：本次模式不覆盖的能力在历史点中返回 `null`。
- `dimension_scores` 数据库默认 `[]` 会把“旧版没有结构化评分”和“结构化评分缺失/未保存”合并为同一状态，无法判断原因。
- 前端 `client/src/App.jsx:4408-4410` 把 `null` 交给 `Number()`，最终变成真实可绘制的 0。这是缺失值与 0 混淆的直接位置。
- 能力条宽度的 `dimension.score || 0` 只影响 CSS 宽度，卡片已先过滤未观测维度，不是曲线污染根因。

应有的三态目前只实现了一半：

| 语义 | 当前存储 | 后端能力 | 前端曲线 |
|---|---|---|---|
| 真实 0 | `score:0` | 有效 0；再受难度加分影响 | 显示 0 |
| 本模式不适用 | 无对应统一能力字段 | `null` | **错误显示 0** |
| 缺失/解析失败 | 新请求通常拒绝；旧库为 `[]` 或字段缺失 | 通常跳过 | 无能力点；但无法区分缺失原因 |

## 三、训练模式 × 能力维度映射

“✓”表示该模式至少有一个评分子维度投射到该能力；“—”表示不评估，正确语义应为 `applicable:false/rawScore:null`。

| 训练模式 | 逻辑推进 | 防守稳定 | 反压能力 | 战场控制 | 表达效率 |
|---|---:|---:|---:|---:|---:|
| 立论训练 | ✓ | — | — | ✓ | ✓ |
| 攻辩小结 | ✓ | — | ✓ | ✓ | ✓ |
| 自由辩论 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 攻辩训练 | ✓ | — | ✓ | ✓ | ✓ |
| 防守训练 | ✓ | ✓ | ✓ | — | ✓ |
| 结辩训练 | ✓ | — | — | ✓ | ✓ |

具体来源：

| 模式 | 子维度投射摘要 |
|---|---|
| 立论 | 辩题理解→逻辑 70%/战场 30%；论证结构、论据→逻辑；战场设计→战场；表达→表达 |
| 小结 | 内容提炼→战场 70%/逻辑 30%；战场结算→战场；漏洞转化→反压 70%/战场 30%；主线连接→逻辑 60%/战场 40%；表达→表达 |
| 自由辩 | 战场识别→战场；回应反击→防守/反压各 50%；逻辑推进→逻辑 70%/战场 30%；表达→表达；战术判断→战场 70%/反压 30% |
| 攻辩 | 问题精准→反压 60%/逻辑 40%；连续追问→反压 70%/战场 30%；抓漏洞→逻辑 60%/反压 40%；压迫推进→战场 60%/反压 40%；表达→表达 |
| 防守 | 正面回应→防守 80%/逻辑 20%；逻辑防守→防守 60%/逻辑 40%；切割识别→防守 60%/逻辑 40%；反压→反压 70%/防守 30%；表达稳定→表达 70%/防守 30% |
| 结辩 | 战场整合→战场 80%/逻辑 20%；成果吸收→战场；价值判断→战场 60%/逻辑 40%；逻辑表达→逻辑 60%/表达 40%；时间结构→表达 70%/逻辑 30% |

这些不是六套对同一能力的等值测量。例如“逻辑推进”可能来自立论证据链、防守切割或结辩收束；“反压能力”可能来自追问、临场反击或防守反压。代码把它们直接放入同一曲线，但没有跨模式等值研究或模式偏差修正。因此它们可以作为训练反馈指标，尚不能被视为严格统一的心理测量量表。

## 四、问题清单

### P0：会直接导致能力值错误

#### P0-1 旧版子分未归一化，72 分记录生成 22.1 综合锋力

- 状态：**已修复（读时适配，不覆盖历史数据库）**。
- 代码位置：`server/src/abilityProfile.js:435` `projectAbilityDimensions()`。
- 触发条件：历史 `dimension_scores` 的 `maxScore != 100`。
- 实际影响：16 条记录、7 个画像受到影响；用户样本所在画像的防守稳定长期停在 23.6，因为后续没有覆盖防守的训练去稀释错误旧值。
- 根因：评分总分函数知道 `score/maxScore*100`，能力投射函数只读 `score`。
- 修复：统一先经过版本化 `normalizeStoredDimensionObservation()`；旧记录按 `score/maxScore*100` 恢复百分制，新记录直接使用 `rawScore`。
- 历史影响：有。
- 数据库迁移：建议先加字段/版本，再离线校验和回填；也可以先做只读兼容适配器，不直接改旧 JSON。
- 测试：真实夹具 `22/30、18/25、14/20、12/15、6/10` 应投射为约 `73.3、72、70、80` 量级，而不是 20 左右。

#### P0-2 不适用/null 在前端变成 0，制造防守与反压锯齿

- 状态：**已修复**。
- 代码位置：`client/src/App.jsx:4405` `AbilityTrendCardInteractive()`，`const value = Number(rawValue)`。
- 触发条件：当前训练不覆盖图表维度；后端正确返回 `null`。
- 实际影响：防守稳定在立论、小结、攻辩、结辩处显示 0；反压在立论、结辩处显示 0；来源卡片会把无关训练展示成该维度 0 分。
- 修复：先判断 `rawValue === null || rawValue === undefined`，保留 `value:null`；折线应分段或跳过，不应把缺失点连接成 0。
- 历史影响：无，只是展示错误。
- 数据库迁移：不需要。
- 测试：混合 `defense → constructive → defense`，中间后端值为 null，前端有效点集合不得包含 0。

#### P0-3 完整数组中的错误字段名会被按位置冒充正确字段

- 代码位置：`server/src/scoringRubrics.js:361-372` `calculateWeightedScore()`。
- 触发条件：AI 返回 5 个对象，但某个名称拼错/升级后改名。
- 实际影响：错误字段不会报错，会按同一索引或首个未用索引赋给另一个 rubric 维度，随后保存时又被改写为规范名称，原始错误被掩盖。
- 修复：在线新数据必须严格按名称一一匹配；位置适配只能放入明确 `scoringVersion` 的旧版迁移器。
- 历史影响：无法从已被重写的记录判断是否发生过。
- 数据库迁移：新数据不需要；历史只能按版本审查。
- 测试：5 个字段中替换一个为未知名称，必须抛 `SCORING_DIMENSIONS_INVALID`。

#### P0-4 旧自由辩字段没有版本适配

- 状态：**已随旧数据读时归一化一并修复**。
- 代码位置：`server/src/abilityProfile.js:32-75`、`:435`。
- 触发条件：历史字段“团队协同与战术意识”；当前字段为“战术选择与临场判断”。
- 实际影响：10 条自由辩记录的第五子维度完全不参与战场控制/反压投射；其中 4 条同时受旧子分制问题影响。
- 修复：按版本建立明确 alias 和旧版投射规则；不要全局模糊匹配。
- 历史影响：有。
- 数据库迁移：可用读时适配；正式回填时需保存 `sourceScoringVersion`。
- 测试：旧字段夹具应按旧版规则转换，未知字段仍应拒绝。

### P1：不会全部错误，但造成明显失真

#### P1-1 难度校准是未经验证的固定平移

- 位置：`server/src/abilityProfile.js:77-81`、`:395-405`。
- 公式：新手 `-4`、校赛 `+2`、市赛 `+7`。
- 影响：同一个原始 70 分会变成 66/72/77。当前库中市赛占 66/102，画像受到系统性正向偏移；该做法还与提示中的“不得固定平移”相矛盾。
- 修复：短期按难度分层展示；中期使用锚题/同稿多难度配对数据估计等值映射。
- 历史/迁移：需要保留 difficulty；不必改原始分，重新计算估测即可。
- 测试：固定回答跨三难度的配对回归和单调性/等值误差测试。

#### P1-2 顶部、曲线和来源卡片口径不一致

- 位置：`server/src/abilityProfile.js:216-238`；`client/src/App.jsx:4505-4523`。
- 影响：曲线点是累计平滑值，卡片总分是单次训练总分，页面没有单次投射原始能力分。用户自然会把三者误认为同一分数。
- 已确认的最终产品口径（2026-07-29）：来源卡同时展示以下三个值：
  1. **本次训练总分**：该条训练记录的原始总分；
  2. **本次当前维度投射分**：仅使用该次训练的模式子维度，按能力投射公式计算出的当前所选能力分，不混入此前历史；
  3. **纳入历史后的综合锋力估测**：把该次训练加入此前有效历史后，当时形成的综合锋力平滑估测。
- 公式语义：本次当前维度投射分不是把最终总分再次拆分，而是与总分共同来源于该次训练的模式子维度。查看五个具体能力时读取 `projectedScores[selectedDimension]`；查看“综合锋力”时，需将该次训练实际覆盖的 `projectedScores` 按综合锋力权重重新归一化，生成独立的 `projectedOverall`，不能读取不存在的 `projectedScores.overall`。难度修正前后的展示口径待新版难度修正公式确定，但内部应分别保留原始投射值与校准后观察值。
- 当前差距：来源卡现在把曲线平滑快照 `point.dimensionScore` 标成“维度分数”，没有提供本次单独投射分，也没有把“纳入历史后的综合锋力估测”作为独立字段明确展示。
- 修复：曲线仍展示历史平滑估测；来源卡新增本次所选维度的单次投射分，并单独展示该历史时点的综合锋力估测。无需为了这三个值增加第二条曲线。
- 历史/迁移：要精确展示旧原始值需版本适配；新记录不需迁移。
- 测试：同一来源卡必须包含 `source.score`（本次总分）、`source.projectedScores[selectedDimension]` 或综合图上的 `source.projectedOverall`（本次当前维度投射分）、`point.overall`（纳入历史后的综合锋力估测）；三者不得复用同一个字段。

#### P1-3 总分设 30 分硬下限

- 位置：`server/src/scoringRubrics.js:404`。
- 影响：所有原始维度均为 0 时总分仍为 30；生产库已有 2 条这种记录。总分与维度口径不守恒。
- 修复：真实计算值使用 0～100；如产品不希望显示低于 30，应另设展示等级或“无效作答”，不能修改统计值。
- 历史/迁移：历史全零记录需确认是真实作答还是测试/失败数据，不能直接删除。
- 测试：全零总分应为 0 或被判为无效，不能是 30。

#### P1-4 没有评分版本，历史无法可靠重放

- 位置：数据库 schema；`validateTrainingRecordPayload()` 写入对象。
- 影响：无法区分 AI 直接总分、旧子分、当前百分制、权重版本、字段版本；75 条百分制记录用当前权重复算也并非全部等于库存总分。
- 修复：新增 `scoring_version`、`rubric_id`、`projection_version`、`estimator_version`；保存完整权重快照或可追溯版本。
- 历史/迁移：需要可空字段的增量迁移；旧值标记 `legacy_unknown` 或可证明的版本。
- 测试：每个历史版本夹具必须由对应适配器重放。

#### P1-5 单样本立即显示一位小数，没有最低样本量和不确定性

- 位置：`server/src/abilityProfile.js:216-309`。
- 影响：1 条记录即可显示如 83.7，并参与综合锋力和辩位推荐；精度看起来高于证据强度。
- 修复：1～2 条显示“试测值”；每维至少 3 条再显示正式估测；同时展示样本数/覆盖模式。
- 迁移：不需要。
- 测试：0、1、2、3 条的状态与展示门槛。

#### P1-6 无异常值处理，评分漂移也没有监控

- 位置：`calculateDimensionProfile()`。

- 测试：70/72/100、连续极值、模型版本切换、锚题漂移。

- 位置：`server/src/abilityProfile.js:192-207`。
- 影响：只完成一次立论即可用逻辑、战场、表达生成综合锋力，防守和反压完全缺失但不会拉低；不同用户的“综合”可能基于不同维度集合。

- 迁移：不需要。

- 影响：评分代码允许 1 位小数，但库存总分为整数；真实样本 B 当前复算为 73.2、库存为 72，除版本差异外数据库类型也无法保存 73.2。

- 迁移：需要安全的列类型变更或新增 `score_v2 numeric(5,1)`。

#### P1-9 未知模式会静默按自由辩投射

- 影响：将来新模式/旧别名可能被错误解释为自由辩，不会暴露异常。
- 修复：未知模式不进入估测并记录可观测错误；只有版本适配器可映射别名。

### P2：算法和展示可继续优化

- `trend` 比较的是“当前全部记录”与“去掉最后 5 条后的画像”，不是上一条，也不是固定时间窗；应明确叫“近 5 次变化”并处理不足 5 条。

- `overallEstimate=300～900` 只用于等级和部分上下文，顶部显示 `/100`，同一 API 暴露两套量纲，建议移除未展示量纲或明确命名为等级分。

- 角色推荐在部分维度可用时会筛选可计算角色，但没有样本门槛和不确定性。

## 五、现有算法公式

以下是当前实际执行公式，不是建议公式。

### 5.1 训练总分

对模式评分子维度 \(i\)：

```text
normalized_i =
  score_i                              , maxScore_i = 100
  score_i / maxScore_i * 100           , otherwise

normalized_i = round1(clamp(normalized_i, 0, 100))
trainingTotal = round1(clamp(Σ(normalized_i * rubricWeight_i / 100), 30, 100))
```

字段名优先精确匹配；失败时会按数组位置兜底，这是 P0-3。

### 5.2 模式子维度投射为统一能力

对统一能力 \(k\)：

```text
projected_k =
  Σ(storedScore_j * rubricWeight_j * projectionShare_jk)
  / Σ(rubricWeight_j * projectionShare_jk)
```

仅统计名称精确匹配且分数在 0～100 的子维度。这里使用 `storedScore_j`，**没有使用 `storedScore_j/maxScore_j*100`**，形成旧数据错误。

### 5.3 难度修正

```text
difficultyBonus(novice) = -4
difficultyBonus(campus) = +2
difficultyBonus(city)   = +7

abilityObservation_k = clamp(projected_k + difficultyBonus, 0, 100)
```

### 5.4 单项能力历史聚合

同一能力只取覆盖它的训练。相邻两次有效更新间隔达到 30 天就开启新包。

包内第 \(i\) 条、其后还有 \(x_i\) 次有效更新：

```text
weight_i = exp(-0.15 * x_i)
packageScore = Σ(score_i * weight_i) / Σ(weight_i)
```

第一个包：

```text
estimate_1 = packageScore_1
```

后续包含 \(n\) 条：

```text
alpha(n) = 0.4 + 0.4*n/(n+2)
estimate_t = alpha(n)*packageScore_t + (1-alpha(n))*estimate_(t-1)
```

这不是简单平均，也不是线性回归或标准预测模型；它属于自定义的分段指数加权平滑。

### 5.5 综合锋力

五项权重：

```text
逻辑推进       3/14  = 0.2142857
防守稳定       4/21  = 0.1904762
反压能力       4/21  = 0.1904762
战场控制       3/14  = 0.2142857
表达效率       4/21  = 0.1904762
```

仅使用已有估测的维度，并重新归一化：

```text
overall = Σ(estimate_k * weight_k) / Σ(observedWeight_k)
coverage = round(Σ(observedWeight_k) * 100)
overallEstimate = round(300 + 6 * clamp(overall, 0, 100))
```

所以“综合锋力”不是 AI 独立评分、不是训练总分别名，也不是简单五项平均；它是五项历史平滑估测的固定权重合成。

## 七、统计与产品合理性评分

| 项目 | 评分 | 理由 |
|---|---:|---|
| 数据完整性 | 43/100 | 11 条无维度、16 条旧量纲、10 条旧字段、无版本和适用性字段；但当前新写入有严格五维校验 |
| 评分口径一致性 | 44/100 | 六模式有明确 rubric 和确定权重，但跨模式同一能力并非等值测量，难度固定平移未经校准 |
| 统计稳定性 | 54/100 | 有近期指数权重和 30 天阶段融合；但无最低样本、异常值处理、题目/模式/难度效应控制 |
| 可解释性 | 36/100 | 公式可复现，但顶部、曲线、单次总分和来源卡口径没有向用户解释 |
| 抗异常能力 | 27/100 | `null→0`、旧量纲、字段位置兜底均可污染；没有版本门禁和稳健估计 |
| 产品展示合理性 | 30/100 | 精确小数和“能力估测”显得科学，但不展示样本充足度、单次原始点或不可比性 |
| **综合** | **41/100** | 平滑框架有一定合理性，但当前输入口径和展示错误使结果不适合直接作为统一能力判断 |

逐项判断：

1. 当前算法在数据版本统一、模式口径稳定时能反映一部分近期变化；当前生产数据不满足这些前提。
2. 单次波动会被指数权重放大，尤其最新值；跨 30 天后的新包首条权重 `alpha(1)=0.5333`，可一次改变超过一半的阶段估测。
3. 不同辩题、模式、难度没有充分可比性。题目效应未建模，模式定义不同，难度仅固定加分。
4. 单样本显示一位小数不合理；它表示计算精度，不表示测量精度。
5. 当前曲线会被前端伪 0、旧版子分和真实异常值污染。
6. 模型评分整体变宽松会被解释为能力上涨，因为没有模型/提示版本和锚答集漂移监控。
7. 存在明显“计算形式科学、测量口径不统一”的问题：指数公式复杂度高于输入数据治理成熟度。
8. 用户无法仅从页面理解曲线点、顶部估测与训练总分的关系；用户提出的疑问是当前展示的必然结果，不是误解。

顶部数值可以称为“历史平滑能力指标”，但在修复版本/量纲/缺失值之前，不宜称为严格的“能力估测”或预测值。它不是历史简单平均，也不是趋势预测。

## 八、推荐算法与数据结构

目标是优先修复语义和版本，再使用简单、稳定、可解释的统计方法。

### 8.1 推荐数据结构

```json
{
  "dimension": "防守稳定",
  "applicable": true,
  "rawScore": 72.5,
  "weightedContribution": 10.9,
  "scoringVersion": "v3",
  "rubricId": "defense-v3",
  "projectionVersion": "ability-v3",
  "mode": "防守训练",
  "difficulty": "市赛"
}
```

不适用：

```json
{
  "dimension": "防守稳定",
  "applicable": false,
  "rawScore": null,
  "weightedContribution": null,
  "scoringVersion": "v3",
  "mode": "立论训练",
  "difficulty": "市赛"
}
```

缺失/失败还应与不适用分开：

```json
{
  "dimension": "防守稳定",
  "applicable": true,
  "rawScore": null,
  "weightedContribution": null,
  "status": "parse_failed",
  "errorCode": "AI_FIELD_MISSING"
}
```

### 8.2 推荐计算步骤

1. **严格写入校验**：模式必须已知，字段名必须精确匹配，五个模式子维度完整；不再按位置兜底。
2. **版本化归一化**：任何估测只读统一 `rawScore 0～100`。旧 `maxScore !=100` 先做 `score/maxScore*100`；旧自由辩字段按旧版本规则适配。
3. **贡献与能力分分离**：总分贡献只用于训练总分；能力画像只用原始百分制投射值。
4. **难度先分层**：第一阶段取消未经验证的 `-4/+2/+7` 混算，按难度分别展示；积累同稿/锚题样本后再估计等值映射。
5. **简单近期估测**：每项取最近 12 个有效、同口径观察，权重 `0.85^age`；缺失完全排除。样本达到 5 后，对明显异常值使用预先固定的稳健规则。
6. **样本门槛**：1～2 条显示“试测”；至少 3 条显示能力估测；正式综合锋力要求五维各至少 2 条，否则显示“画像未完整”。
7. **来源卡三口径**：曲线继续展示历史估测值；来源卡分别展示本次训练总分、本次当前维度投射分、纳入历史后的综合锋力估测。不适用维度的单次投射分为 null，不得显示为 0。
8. **漂移监控**：每个模型/提示版本跑固定锚答集，若平均变化超过预设阈值，不与旧版直接合并。

推荐估测公式：

```text
取最近最多 12 个有效观察 x_t
weight_t = 0.85^(最新观察与该观察之间的有效更新次数)
estimate = Σ(weight_t*x_t) / Σ(weight_t)
```

该方案比当前“30 天分包 + 动态 alpha”更容易解释和测试。若业务确认 30 天训练阶段有明确含义，也可以保留分包，但必须先完成版本、量纲、缺失语义和难度等值治理。

### 8.3 历史修复顺序

## 十一、结论

审计发现的异常不是用户观察偏差：

- **72 → 22.1** 是旧分制兼容缺陷，现已通过读时归一化修复；
- **防守大量 0、反压锯齿** 是前端把不适用 null 转为 0，现已修复；
- **顶部与最新训练不同** 是因为顶部和曲线使用历史平滑估测，不是最新一次分数；
- 但这一平滑估测同时混合了不同模式、不同难度和不同评分版本，所以当前统计解释力有限。

建议先完成 P0 的小范围修复和历史读时适配，再讨论是否替换平滑算法。当前最需要解决的不是增加更复杂的统计公式，而是保证每个输入点确实是同一量纲、同一语义的有效观察。
